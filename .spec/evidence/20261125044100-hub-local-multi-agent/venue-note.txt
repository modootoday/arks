Topology: one `arks serve --no-ssh` process on loopback serves the forge API and smart
HTTP for the forge's local/playground Git directory. Each agent is its own forge account:
own HOME, token file and hosts file, logged in with its own token through
`arks auth login --with-token`. Agents act at once (threads released by a barrier, each
spawning the arks binary); the runner never spawns gh or git.

Product bugs the scenarios exposed and the tip fixes (host-observed before the fixes):
  - issue edit / pr edit label and assignee changes were read-modify-write of the whole
    set, so concurrent agents dropped each other's labels (HUB-MA-05 failed);
  - pr view --json files / commits were always empty, comment rows had no id;
  - /user/keys, /user/gpg_keys and /gists showed and deleted every account's data, and
    @me projects resolved to the forge default user (HUB-MA-10 failed on ssh-key delete).
Known gap, not part of these rows: the arks smart-HTTP fetch does not store tags, so
HUB-MA-06 reads the tag with ls-remote (separate task).

Scrub: SSH key-type names with an at sign before `openssh.com` (from `ssh-key` output in HUB-MA-10) are written `name[at]domain`, because the public-surface scan reads them as e-mail addresses; the driver applies the same rule on later runs. No other byte changed.
