# Git wire protocols

## Question

What wire framing, capability negotiation, and transport bindings must GIR implement to interoperate with stock Git clients and servers?

## Method

Primary gitprotocol-common, gitprotocol-capabilities, gitprotocol-pack, gitprotocol-http, gitprotocol-v2; cross-check legacy aliases pack-protocol / http-protocol. SSH/git/file share pack protocol semantics per those docs.

## Findings

### Shared framing — gitprotocol-common

- **URL:** https://git-scm.com/docs/gitprotocol-common
- ABNF (RFC 5234 style with Git’s HEXDIG tweak).
- **pkt-line:** 4 hex length bytes including themselves; max payload 65516; flush-pkt `0000`; empty `0004` discouraged; LF rules for non-binary lines.
- Refname rules shared with ref storage (see [[research:root/20261108071914]]).
- **Compat impact:** all smart transports depend on exact pkt-line behavior.

### Capabilities (v1) — gitprotocol-capabilities

- **URL:** https://git-scm.com/docs/gitprotocol-capabilities
- Advertised on first ref or `capabilities^{}` line; space-separated.
- Includes (non-exhaustive; see page): `multi_ack` / `multi_ack_detailed`, `no-done`, `side-band` / `side-band-64k`, `ofs-delta`, `agent`, `object-format`, `symref`, `shallow`, `deepen-since`, `deepen-not`, `deepen-relative`, `no-progress`, `include-tag`, `report-status`, `delete-refs`, `quiet`, `atomic`, `push-options`, `allow-tip-sha1-in-want`, `allow-reachable-sha1-in-want`, `filter`, etc.
- **Compat impact:** never advertise a capability GIR does not implement; ignore unknown optional peer caps per documented rules.

### Pack protocol (ssh / git / file) — gitprotocol-pack

- **URL:** https://git-scm.com/docs/gitprotocol-pack
- Fetch path: upload-pack ↔ fetch-pack; push path: receive-pack ↔ send-pack.
- Ref advertisement, want/have negotiation, shallow/deepen/filter lines, packfile transfer (optionally sidebanded).
- HTTP details deferred to gitprotocol-http; pack bytes to gitformat-pack.
- Legacy mirror: https://git-scm.com/docs/pack-protocol

### HTTP dumb + smart — gitprotocol-http

- **URL:** https://git-scm.com/docs/gitprotocol-http
- Dumb: static `info/refs`, `objects/info/packs`, loose/pack GETs (needs `update-server-info`).
- Smart: `GET $GIT_URL/info/refs?service=git-upload-pack|git-receive-pack` with advertisement Content-Type; then `POST` to service with request/response types.
- Stateless server; clients SHOULD support Basic auth; cookies not required for correctness.
- Smart clients may fall back to dumb when advertisement content-type is wrong.
- Cites HTTP URL syntax / auth RFCs as referenced in-page.
- Legacy mirror: https://git-scm.com/docs/http-protocol

### Protocol v2 — gitprotocol-v2

- **URL:** https://git-scm.com/docs/gitprotocol-v2
- Capability/command oriented; ls-refs, fetch, object-info, bundle-uri (as advertised).
- Designed for HTTP/stateless-rpc; flush semantics clarified vs v1.
- Shallow and filter arguments mirrored with v1 meaning where featured.
- **Compat impact:** modern hosts expect v2; GIR should speak v2 and still understand v1 peers.

### SSH / git / file transports

- Pack protocol doc states ssh://, git://, and file:// use the same pack protocol; HTTP is separate.
- SSH invocation of `git-upload-pack` / `git-receive-pack` is described in command man pages (`git-upload-pack`, `git-receive-pack`, `git-shell`) rather than a separate “ssh-protocol” format page.
- `git://` daemon: https://git-scm.com/docs/git-daemon

### Sideband and progress

- Defined under capabilities + pack/v2 docs: sideband multiplexes pack + progress + errors.
- Long-running helper pkt-line: https://git-scm.com/docs/long-running-process-protocol

### Bundle URI / packfile URI

- https://git-scm.com/docs/bundle-uri
- https://git-scm.com/docs/packfile-uri
- Optional v2-era seed mechanisms; negotiate only when advertised.
